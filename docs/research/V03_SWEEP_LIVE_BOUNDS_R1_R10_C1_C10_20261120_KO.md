## Milestone 3 · R3/C3: exact source-row partition and tight structural charge (derived, CAS checked)
Let `n` be the number of supplied finite source Part rows. Define `u=#{i: p_i.b > p_i.a}` for nonpoint intervals and `q=#{i:p_i.b == p_i.a}` for point events. Under the previously enforced admissible interval predicate (no reversed intervals, valid finite clock), **u+q=n**. The old sweep unconditionally reserves 3n `(f64,index)` entries at 16B each and n current point indices at 8B each: `W_old = 56n + 8 ceil(n/64) + 8 ceil(n/4096) + 256` structural bytes for index/event scratch, excluding separate `edge_bytes=16n` and live output buffers. But a nonpoint row inserts *only* one start and one end entry, while a point row inserts *only* one point entry. Thus exact cardinalities are `len(starts)=len(ends)=u`, `len(points)=q`; `current_points` contains a subset of points so has maximum `q`. The actual preallocation can use those counts. Therefore `W_new = 32u + 24q + 8 ceil(n/64) + 8 ceil(n/4096) + 256`. Reduction: `W_old-W_new = 24u+32q >=24n` bytes for nonempty source, with no change to guard cap or floating-point operations. CAS independently simplified the identity to `8(3u+4q)`. For observed previously **completed** cell split maximum n=303,634, counterfactual structural saving is 7,287,216..9,716,288 bytes depending on point fraction; this is NOT an observed saving at the **failed** cell and NOT process RSS. A 2,305-byte deficit would require at least 97 nonpoint rows or 73 point rows to be displaced, if this were the only difference; actual source replay is decisive.

Exactness lemma: the two-pass count only classifies each original `(p.a.unwrap(),p.b.unwrap())` by original `==` and `>`, without arithmetic or data modification. Sorted start/end/point values and indices remain identical multisets, and stable comparator `total_cmp(time).then(index)` yields the same sequences including signed negative zero ordering. `advance(a)` then builds the same active *source indices* in ascending order and the same sorted point index list; all further IEEE mass/birth fsum terms, PacketParts sequence, source birth, FIFO and checkpoint bits remain identical for successful calculations. Count can fail for an invalid reverse interval as the previous sweep did; output equivalence is scoped to valid intervals. This is an algorithmic representation/scratch-life result, not a new traffic model or proof of full-day feasibility.

## Milestone 7 · R7/C7: exact unique-edge multiway merge derivation and counterexample
Once the original three `IntervalActiveSweep` endpoint/index arrays are separately sorted by `total_cmp(time)`, they contain all **numeric** source endpoints: every nonpoint Part contributes `a` to starts and `b` to ends; each point Part contributes `a` to points, with `a==b`. For finite IEEE-754 inputs, two *numerically equal* endpoint values can differ in binary representation only at signed zero. The original `edges` construction materializes `[a_i,b_i]` for each source row, sorts all 2n values by total order and `dedup()` uses numeric `==`: its representative for numeric zero is `-0.0` iff **any** source endpoint has negative-zero bits. Therefore a three-way merge of already sorted starts, ends and points, emitting one representative for each numeric equality class and correcting zero sign from one source negative-zero flag, produces exactly the original ordered bit-pattern edge vector. It does not change original `IntervalActiveSweep.advance`, Part/source order, event clock, route, mass/birth or f64 reduction.

A two-pass O(n+k) iterator over three sorted arrays can **count** k distinct numeric edge classes, then allocate `Vec<f64>` with k slots and fill in identical sorted order. Relative to the old `edges=checkpoint_vec(2n)` and scratch charge 16n bytes, this reduces live edge vector to `8k`, structural difference `8(2n-k)` bytes, while leaving `event_index_bytes`, active bits and retained output charges alone. Source validation supplies finite times; `-0/+0` may remain point values with different source endpoint bits, only the *edge representative* follows sorted/dedup convention. This is a genuine memory and sorting-work algorithm improvement, not a budget discount or a guarantee of downstream success. The separate counterexample `Part.a=+0.0, Part.b=-0.0` would be misrepresented if points provided only a and no zero-sign correction; the construction explicitly retains the sign flag. Another edge case `Part.a=-0.0, b=+0.0` has numeric point classification; it contributes the same numeric class with original negative-zero edge representative.

Failure/performance gate: before sorted event arrays can allocate, retain source work preflight for the counted index workspace; after deriving unique count, preflight the exact current edge bytes plus index bytes, then allocate the unique edge vector.
