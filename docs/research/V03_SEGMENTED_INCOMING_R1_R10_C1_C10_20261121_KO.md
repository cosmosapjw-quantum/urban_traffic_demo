## R3/C3 · Exact row-order lemma and structural live-buffer bound (derived + CAS arithmetic)

Define `G` = road destination cell count, `R` = the cumulative conservative incoming logical row count already charged by `work.transfer` during the live step, `B=64` = number of `Part` values per fixed chunk, `P=size_of::<Part>()=48`, `M=size_of::<Mark>()=16`, `H=size_of::<Vec<Part>>()=24` on the pinned x86_64 host. Each cell `j` receives an ordered sequence `p_{j,0},...,p_{j,r_j-1}` with source indices preserved. Store this sequence as append-only pages of **exactly B slots** with the last possibly partially used: `p_{j,i}` is at chunk `floor(i/B)` and offset `i mod B`. Thus concatenating all pages returns the identical source list, including duplicate keys, negative-zero time bits, and f64 masses/births. No old page is copied when a new row is appended.

Original `incoming+marks` guard term: `E_old(R)=2R(P+M)=128R`, a conservative dual-capacity allowance during growth of both single-Vec families. New page-backed Part payload is at most `P(R+(B-1)G)`: each nonempty cell wastes at most B-1 trailing page slots and the cumulative charged R upper-bounds actual pushed rows. Page-vector metadata under the *same existing Rust doubling envelope* is conservatively `2H(ceil(R/B)+G)`. Marks continue their unchanged original conservative `2MR`. Hence `E_page(R,G)=R(P+2M)+P(B-1)G+2H(ceil(R/B)+G)` for `R>0`, and zero if no incoming has been charged; these are **structural allocation terms**, not entire resident RSS or a compiler-independent proof of Vec allocator capacities. Explicit page capacity and page header bounds will be asserted in the implementation/test on the pinned Rust runtime. For the observed C8 second-tick transfer trace `R=7,968,194`, `G=1,586`, the old expression is `1,019,928,832` bytes, the candidate new expression is `648,303,904` bytes, potentially removing `371,624,928` bytes from that **named** work charge. Wolfram evaluated the integers independently. This does not assume all bytes are resident at that exact transfer site, nor predict an automatic 24h completion.

**Exactness of source-index grouping:** Define the original combine key `K(p)=(tag,offset,a_bits,b_bits)` and its original stable source tie breaker `i`. For every source list `P=(p_0,...,p_{n-1})` the sorted filtered indices are `I=sort({i|p_i.mass>0}, (K(p_i),i))`. A page indexing function `P[i]` returns precisely the same `Part` without floating arithmetic; therefore the same sorted I and each contiguous equal-key group are obtained, and the original `sum` routine sees the identical ordered mass and birth bit patterns. Output Part keys and group order are identical; no provenance from separate cell streams is merged before the original combining stage. This is a constructive representation isomorphism conditioned on faithful page indexing, **not** a no-go theorem or change in physical closure.
