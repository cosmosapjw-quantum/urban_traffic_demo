## R2/C2 · FIFO representation literature and code/event ownership map

Primary literature checked: Bar-Gera & Carey, *Representation requirements for perfect first-in-first-out verification in continuous flow dynamic models*, Transportation Research Part B 100 (2017), 284–301, DOI https://doi.org/10.1016/j.trb.2017.02.002, demonstrates that the information required for network-wide perfect FIFO depends on the solution representation (its abstract distinguishes eight notions, seven essentially equivalent and one weaker). Bar-Gera & Carey, *Constructing a cell transmission model solution adhering fully to first-in-first-out conditions*, Transportation Research Part B 161 (2022), 247–267, DOI https://doi.org/10.1016/j.trb.2022.04.002, demonstrates a computationally expensive exact-FIFO CTM benchmark, not a claim that arbitrary micro-event rows can be deleted. This source-specific page implementation is **our direct code-level derivation**, not a result claimed by either paper.

The actual `V1Road::step_state` originally builds one `Vec<EventRow>` in the order it iterates eligible served packet rows, plus `ChunkedParts`/ `ChunkedMarks` for incoming per-destination values. The trace from the last physical failed 100k Valley tick recorded `events_len=9,100,145`, `events_cap=16,777,216`, `entry.raw_rows=8,985,190`, `entry.combined_rows=8,751,385`, 6,319,329 recurring adjacent route keys but only 149,622 recorded equal-density adjacent rows. Shared route keys alone do not prove equal mass, birth, time interval endpoints or original `f64` reduction equivalence. An arbitrary per-row coalescence would violate original event order and physics; it is **not** adopted.

The road step returns an ordered `Vec<EventRow>` consumed by native service/journey; checkpoint wire still requires exact original field order. The raw candidate can be temporarily paged until the step's road workspaces are released, and then flattened without arithmetic or reordering. The new payload and metadata during append are actual independent allocations, so the old conservative three-copy reallocation envelope can be replaced by a per-page upper bound. However the flattening phase briefly holds *both* pages and the final flat Vec; it must be explicitly bounded, not hidden. The original process address-space cap stays unchanged. Unrelated model alternatives (partial FIFO, link transmission, kinetic) require a new physical model acceptance and are not allowed to increment the exact FIFO V03 plan.

## R3/C3 · Exact source-order paging theorem and two-phase memory envelope

Let `E` be the cumulative logical event count charged by `RoadWorkBudget::transfer`, `N` the actual events materialized, `0<=N<=E`, `B=4096` fixed EventRow slots per page, `W=sizeof(EventRow)=64B`, `H=sizeof(Vec<EventRow>)=24B` on the pinned x86_64 Rust ABI. A new candidate event `e_i` is appended to page `i div B`, slot `i mod B`; all completed pages are immutable until moved into the returned contiguous row vector. Iterating these pages in ascending page and slot order returns **exactly** `e_0,...,e_{N-1}` with unchanged tag/source/destination, mass, start/end, birth bits. This is a constructive order-preserving bijection, not aggregation; no route/event is discarded.

Original push-built candidate resource term is `C_old(E)=3 max(E,4) W +96` for `E>0` (0 candidate records yields +96 fixed tag/control allowance). Actual page payload during append is <= `W(E+B-1)`; the Vec-of-page descriptors can transiently hold old and grown allocations, conservatively <= `3H(ceil(E/B)+1)` under original doubling, checked at runtime. Thus page-candidate structural upper `C_page(E)=W(E+B-1)+3H(ceil(E/B)+1)+96` for `E>0`, `C_page(0)=96`. When flattening after road work, the pages and final `Vec<EventRow>` coexist temporarily; add an explicit `N W` *separate phase* allowance before the final flat allocation rather than hiding it. This preserves both original process limit and physical event row count. Actual page capacity and Vec headers are measured in tests; neither a `Vec` allocator general theorem nor measured RSS is claimed.

For the observed prior physically generated `E=9,100,145`, Wolfram evaluated `C_old=1,747,227,936 B`, `C_page=582,831,512 B`, direct candidate-workspace reduction **1,164,396,424 B**. Even including a new final contiguous event array of `E W=582,409,280 B`, the conservative simultaneous page+flat envelope is `1,165,240,792 B`, still **581,987,144 B** smaller than the original 3× conservative push-growth envelope, ignoring any other identical phases. At lower N this is an upper-bound comparison, not direct process RSS or an assurance that the next service/journey phase passes. Source `trace.event_len` and native resource guard must be independently measured on the old 1.9GB checkpoint.

The lemma has no extra traffic-model assumption: `EventRow` fields and their ordered appearance into service and original checkpoint are identical under the same finite source and native arithmetic. `Mathbox computation audit` finite assertion: verify exact expression at E=9,100,145, B=4096, W=64, H=24 and its implied nonnegative saving; success does **not** establish whole-run memory monotonicity or scientific novelty.
