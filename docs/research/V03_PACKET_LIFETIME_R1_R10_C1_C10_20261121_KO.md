## R2/C2 · Original FIFO literature and source lifetime investigation

Verified from the exact parent Rust code at `crates/metroflow-rust/src/v1_road.rs`: `RoadWorkBudget::transfer` adds new incoming raw Part/Mark row counts to the single monotone `self.incoming` counter; `RoadWorkBudget::require` uses `segmented_incoming_charge_for(self.incoming,self.incoming_page_cells,...)` for **every later phase**. But during second part of `V1Road::step_state`, after the complete source transfer, the road processes *each destination cell in index order*. For each cell `i`, `marks[i]` are read to compute weighted speed and latent moments and then never accessed again. `incoming[i]` source pages are moved into local `source`, all original rows are losslessly combined into `parts` via sorted source indices and exact original IEEE `sum`, then `drop(source)` destroys those source pages. The source still holds the **unneeded original `marks[i]` fixed page arrays** until the end of the whole step, and the `work.incoming` charge is never reduced despite `incoming[i]` being physically freed. Under trace record, the diagnostic-only `incoming_src[i]` is also kept after its `exact_merge_census` use. This is an actual source-lifetime defect and live allocation opportunity, independent of exactly how many physical packet cohorts must survive.

The original 25,690→25,700 failing tick after a 30s continuous prefix: `road_work:packet interval packing` required 5,026,043,552 against 5,026,041,759, excess 1,793B, cumulative 13,915,377 incoming rows and 92,142 interval-packing checks, while the fresh identical-input reloaded tick stalled at `entry interval split` required 5,087,568,488 against 5,087,563,191, excess 5,297B. Different source session lifetimes mean these are distinct guard traces, not proof of changed physics. The physically distinct source rows in packets and their route/f64 birth histories must NOT be removed. An exact source buffer may be dropped **only after** all computations requiring its original values are complete; its presence must be removed from subsequent source-bound resource accounting **at that actual lifetime boundary**. The original correct FIFO work cannot be changed from a hash-key collision or merely a lower numeric guard.

Primary traffic literature checked through Exa/SciSpace/Parallel: H. Bar-Gera and M. Carey (2017), *Representation requirements for perfect first-in-first-out verification in continuous flow dynamic models*, Transportation Research Part B 100, 284–301, https://doi.org/10.1016/j.trb.2017.02.002, identifies strict network-wide FIFO representation requirements including cohort bundles and distinctions from weaker FIFO; H. Bar-Gera and M. Carey (2022), *Constructing a cell transmission model solution adhering fully to first-in-first-out conditions*, Transportation Research Part B 161, 247–267, https://doi.org/10.1016/j.trb.2022.04.002, constructs a high-complexity benchmark. These do not claim a Rust memory optimizer nor authorize eliminating physical source histories. Our specific lifetime equivalence is a **direct source-derived lemma**, not literature attribution.

Remaining scoped implementation risks: dropping an `incoming[i]` Part page before `combine_chunked_parts` is complete is not allowed; dropping `marks[i]` before computing the original ordered weighted-speed/byclass f64 reductions is not allowed; discounting source rows from `work.incoming` while keeping their Mark pages allocated is unsound. Correct fix couples **both** drops, then decrements only actual discharged `raw_rows`; the retained packet outputs and their `interval_retained` charges remain as before. Preserve unchanged B=128 and compact EventRow/Part codec, original numeric budget; no arbitrary 1.8KB waiver.

## R3/C3 · Exact lifetime release lemma, computational source bound and stop rule

Let `G` be number of destination cell buffers, `R_k` cumulative *charged* original incoming Part+Mark source-row count **still live after k completed destination cells**, `r_i` actual simultaneously present source Part/Mark rows at destination i, B=128, physically allocated source Part page 40B, Mark 16B and Vec-page descriptors 24B. Existing conservative source charge `M(R,G)=56[R+127G]+96[ceil(R/128)+G]` bytes (R>0, zero for R=0), with spare rows and outer Vec growth allowance retained even for all G. Crucially `work.incoming=R_0` in the current source never decreases; after an original cell's weighted-speed and byclass latent f64 reductions, source `combine_chunked_parts`, and original `drop(source)`, neither the cell's raw Part nor its matched Mark page is needed for any later physical operation. Releasing `drop(take(marks[i]))` after last Mark use, and `drop(take(incoming_src[i]))` after read-only trace diagnostic, physically destroys the two raw source arrays. At that **verified actual lifetime** only, execute `work.release_incoming(r_i)` with checked `r_i<=R_k`. The retained exact combined Part output and subsequently packed `PacketParts` are *different owners* already tracked by `interval_retained` and `interval_transient`; they are never erased.

**Lemma (derived):** The original algorithm after completing destination-cell i has no read dependency on `incoming[i]`, `marks[i]`, or diagnostic `incoming_src[i]` before the end of the road step. The ordered physical computations involving them are fully completed **before** release, and `PartIter`, `combine_chunked_parts`, `sum`, road closure and original FIFO source packet order receive exactly the same arguments in the same original order. Thus reducing `work.incoming` by `r_i` after both page allocations have actually been destroyed does **not** modify a single output floating operation or serialized checkpoint field. Its bound remains conservative for all currently live raw source rows because older charged-source discrepancies are positive and no later cell ever reuses released cell's buffer. The exact conservative resource reduction for a nonzero remainder is
`ΔM_i=M(R_k,G)-M(R_k-r_i,G)=56 r_i+96[ceil(R_k/128)-ceil((R_k-r_i)/128)]` bytes.
When no raw rows remain, this can release the entire source charge term (the allocator header/cell descriptor itself remains in source `base`/owner but this charge is for raw pages only). The change is a *real allocation lifetime improvement*, not a cap increase, not a physically approximate packet merge, and does not assert that no later phase can block.

Wolfram exact arithmetic for original failed continuous 100k tick `R=13,915,377,G=1,586`: `M(R,G)=801,129,544B`. Releasing an actual 10,000-row destination after both raw source pages are gone yields `M(R-10000,G)=800,562,056B`, **567,488B reduction** (including source page descriptor bound); this is a finite source-bound assertion, *not* evidence the original worst cell has exactly 10,000 rows. The actual paper's network FIFO representation cannot be simplified to packet mass-only; this lemma concerns **only expired intermediate source buffers**, not any living physical cohort. Source must verify actual per-cell row counts, correct release total, exact retained conservation and true native output via independent original 100k run.
